## Prioritized findings

### P0 — correctness/security gates (do not treat production commerce as fully validated)
1. **Live database access and row permissions not verified.** Screenshots document the shop's stale-data warning, profile's failed live-record refresh, and leaderboard errors. Source uses NEXT_PUBLIC_SUPABASE_URL/ANON_KEY client-side reads. Vercel environment variable presence and successful code build do not prove Supabase project health, correct project URL, API key validity, published schema, RLS or browser network permissions. Connect the owning Supabase organisation and audit request statuses/errors with owner approval. Keep stale-stock ordering disabled.
2. **Customer auth needs server validation.** `app/register/page.tsx` performs bcrypt/login comparison in the browser after selecting members rows; `lib/member.ts` uses a localStorage record and client-set cookie, and `middleware.ts` checks that cookie for member-only route access. This is not independently verified server-side member authentication. Audit member-table SELECT/RLS, account isolation, password hash exposure, admin vs customer sessions, and migrate to server/Supabase Auth before exposing private account/payment data broadly. Admin middleware verifies Supabase user and `current_staff_roles`, which is a useful separate protection; audit per-role table grants/RLS because direct admin module writes are performed in client-side code.
3. **Duplicated product payment confirmation paths.** `app/admin/orders/page.tsx` calls `awardForPayment` and uses `rewards_applied`; `app/admin/members/page.tsx` also lists Orders & Payments and confirms order payment directly without calling the same reward flow. This can create different membership/reward outcomes depending on which screen staff use. Freeze reconciliation assumptions, converge on one server-side idempotent payment-confirmation transaction, then repair records from bank/payment evidence. Do not auto-award backfill based solely on apparent status.
4. **Non-atomic points/expiry updates.** `lib/loyalty.ts` writes members, loyalty_points and points_transactions separately. Order/ticket status flows update their rows separately from reward writes; failures can leave partial outcomes. Fix with one transactional server-side function, idempotency key, audit trail and reversals; compare current outstanding discrepancies before migration.

### P1 — incomplete or misleading customer/admin integrations
5. **Membership expiration is calendar-based, not opening-day-based.** `calcMembershipDays(spendDkk)=spendDkk/20`; `awardForPayment` extends `membership_expires_at` by 24-hour periods, `clawbackForPayment` removes calendar time, and profile calls `daysRemaining`. No official opening-day calendar, pass credit ledger, attendance/automatic-debit agreement, closure corrections or event-based expiry. Distinguish `30/60/90 OPEN days` from `1/2/3 calendar months` before pricing. Decide whether every actual open day consumes one active day, or only verified attendance consumes one; the latter is a separate attendance-credit product and may remain valid much longer. Protect legacy accrued access in a versioned migration. Paid Club Pass checkout and starter-car entitlement are still future plans.
6. **Race minimum/prize/refund is only prospectively described, not backend-enforced.** New fixed event description says six distinct confirmed paying racers, 350 DKK base, +25 per additional distinct paid racer; old sold terms preserved. Existing ticket purchases are not definitively tied to a particular event; client-side `race_entries` count alone cannot certify unique verified payers. `postponed` status compatibility with actual database constraints and all public status readers must be tested. No automated transfer/refund, owner approval, payment-reference check or attendee notification. Validate data model and develop per-event settlement workflow before promising automatic transitions.
7. **Loyalty points policy conflict.** Fixed rewards code awards 1 whole point per cumulative eligible 100 DKK and points_rate=1. `app/admin/seasons/page.tsx` and `app/admin/hall-of-fame/page.tsx` still write tier-based points_rate 2,3,4,5 and 8 into members/loyalty_points. Old tier multipliers and current fixed reward model need clear separation between prestige/racer ranking and financial reward points. No historical point recalculation without approved reconciliation.
8. **News and Gallery demo-edit trap.** `app/admin/news/page.tsx` and `app/admin/gallery/page.tsx` initialize demo records. If DB refresh fails, the UI remains editable locally and save/delete may appear to work without persistence; public pages can show independent data or placeholders. Fail visibly, disable mutations until DB connection is verified, separate demo mode if deliberately desired.
9. **Shop inventory and catalogue image mapping incomplete.** Public shop has a saved-catalog fallback; stale checkout now gated. Actual source image URLs, failed files, product-to-photo matches, stock, shared case inventory and preorder processes require authoritative table and storage access. Do not generate or substitute unrelated images for product listings.
10. **Admin dashboard and various list pages may show zero/empty when read fails.** `AdminDashboardContent` uses empty arrays for failed `Promise.all` reads without per-resource error reporting; many modules have direct client Supabase calls with limited catch/error handling. Use timeout + retry + last verified timestamp and never label unverified zero as real.
11. **Photo consent/leaderboard incomplete.** Public racer photo is optional and default avatar exists, but exact consent creation, revocation, approved URL/storage policy and protection of legal identity are not fully verified against the live database. Avoid mandatory ID photos for public standings.
12. **POS/employee device controls and TimeLog bridge unfinished.** Existing TimeLog remains sole hours source. Managed company-device enrolment, unique staff till actions, owner-only remote admin, refunds/discount approval and tamper-evident transaction logs still require server-side permissions/device enrolment. UI-only/IP-only locks are insufficient.

### P2 — polish and documentation
13. **Tires/Wheels glyph unavailable.** Replace emoji with local accessible SVG across index/detail (contained in current PR). Investigate any other unsupported newer emoji and missing glyphs with Windows/Android/iOS QA.
14. **Navigation is largely wired but needs practical mobile and authenticated browser QA.** Test hamburger close/focus, direct-link reload, long guide/previous/next and stale profile/ticket states. Guide navigation now has visible top/back/bottom links.
15. **Opening-day policy/site copy.** Future paid pass descriptions had one/two/three-month wording. Current branch changes proposed copy to opening-day units, explicitly unsold. Do not switch stored existing calendar-based accrual without data migration and customer approval.
16. **Administrative operations**: add owner action approvals, safe archive instead of destructive record deletion (e.g. orders, tickets, seasons, results), server audit logs and reconciliation export. Current `admin/seasons` explicitly deletes associated race results when a season is deleted.
17. **Race promotions and event texts**: verify every public post/event does not disclose the organiser margin, but keep previous purchaser's agreed event terms accessible privately. Publish exact podium payout allocation, ticket linkage, multi-entry rules, cancellation/postponement and payment instructions before taking live registrations.

## Proposed safe implementation order
1. Connect the ACTUAL Mini4WD Supabase project under authorised account; verify environment project ref without sharing secrets; inspect API/network failures and policies, export read-only backups and reconcile source tables and order/ticket balances.
2. Security/auth and single payment confirmation transaction; resolve duplicate admin payment screens; reconcile reward ledger and historical expiries.
3. Agree membership pricing/consumption semantics and migration rules. Build opening calendar, membership credit ledger, credit reversals/closures, and server-authoritative eligibility; test two-day/week and holiday/extra-opening schedules; separately implement first-time kit promotion with SKU/stock/one-time checks.
4. Complete race event-to-ticket linkage, verified distinct payer count, future announced date, refund/carry-forward choices and per-event prize/podium settlement.
5. Harden dashboard, News/Gallery/stock error states, images/consent, per-role staff device and POS audit, then execute comprehensive real-account QA.

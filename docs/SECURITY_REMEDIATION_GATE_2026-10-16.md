## Read-only verified risk assessment (2026-10-16 / UTC 2026-10-17)
- `public.members` is a UUID table with `email`, `password_hash`, `auth_user_id`; RLS OFF. `anon` has table SELECT and column SELECT on `password_hash`. No actual hash was fetched. The existing `app/register/page.tsx` fetches the whole member row and compares bcrypt in the browser, so removal of that grant BEFORE replacing login would break member login.
- Other business tables including `orders`, `loyalty_points`, `cars`, `race_tickets`, `race_entries`, `race_results`, `tournaments` have RLS OFF and `anon` SELECT/INSERT/UPDATE/DELETE (also TRUNCATE) grants. That is an authorization defect, not proof someone exploited it.
- Security advisor lists **29 RLS-disabled public tables**, plus the `season_standings` SECURITY DEFINER view warning. [RLS linter](https://supabase.com/docs/guides/database/database-linter?lint=0013_rls_disabled_in_public) / [definer-view linter](https://supabase.com/docs/guides/database/database-linter?lint=0010_security_definer_view).
- Current database count-only queries: 7 member rows, **0** linked via `auth_user_id`, 5 cars, 2 tournaments, 2 race results, 1 race entry. `cars` ownership uses email text; official `race_results` uses member UUID. Do not migrate by name.
- Existing staff Auth uses Supabase Auth + `staff_roles` and `is_admin()`; seven previously applied migration entries are in Supabase's history, including auth phase1/phase2 and owner bootstrap.
- Critical application dependency: admin pages `app/admin/{orders,tickets,race-results,cars,tournaments}` use an anonymous direct Supabase client for writes despite authenticated admin middleware. Restricting anon without moving these writes to authenticated, per-role authorized server paths WILL break administration. Member login/register, garage, profile, orders/tickets, referrals and loyalty similarly need audited replacements.
